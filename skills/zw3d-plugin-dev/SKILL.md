# 中望3D插件开发

把一个功能做好，让它自然地加入同一个工具箱。每个插件独立安装、独立升级、独立卸载；共用框架负责按钮、管理和安装事务。

## 从需求开始

先明确功能的输入、输出、会修改什么，以及何时算成功。已有授权和约定继续有效；仅在缺少会改变实现的信息时追问。

选择最小的实现：需要访问当前模型或调用ZW3D进程内SDK，使用DLL模板；文件转换、外部计算等独立任务，可使用EXE模板。独立EXE的工具箱按钮只是启动入口，不自动获得当前模型的访问能力。

开发前读取[包与身份契约](references/package-contract.md)。涉及SDK回调、资源和模型修改时，再读取[宿主与代码边界](references/host-boundaries.md)。需要安装、更新和卸载测试时，读取[验收方法](references/acceptance.md)。

## 保持三个边界

- **功能属于插件。** 业务代码、资源和依赖放在自己的包内；路径从自身模块或应用位置解析。模板里的示例身份必须换成自己的稳定身份。
- **入口属于框架。** 在清单中声明命令，让框架生成“扩展工具”功能区入口。不要另建顶层菜单、重复安装框架，或直接编辑其他插件的UI文件。
- **状态属于用户。** 普通卸载保留设置和日志；“彻底清理”才删除插件自己的数据。安装、更新和卸载遇到运行中的宿主，记录为“等待重启”，不得强制结束用户的中望3D。

SDK名称、签名和返回值以目标机安装的2027 SDK头文件为准。不要从旧例子猜API，不要复制SDK库、宿主程序或用户文件到交付物。

## 写少而完整的代码

从对应模板开始，保留它的加载、注册、退出和错误路径。让一个命令完成一件事，把模型处理与界面回调分开；只在重复出现或需要独立验证时增加抽象。

初始化只建立插件需要的状态。命令注册失败就撤销已注册项；退出释放自己拥有的对象和回调。`DllMain`不做SDK调用、文件安装或复杂初始化。v1不支持运行中卸载DLL。

修改模型的命令应明确失败结果，避免把部分完成记成成功。保存、覆盖和批量处理范围服从用户任务；不要让示例默认覆盖原图。批量操作中的提示必须有明确处理路径，不能留下无人处理的对话框。

错误信息告诉用户哪里失败、现在保留了什么、下一步可以做什么。日志记录可定位的事实；不要把开发细节塞入正常使用界面。

## 用工具完成交付

优先使用本技能随附的`assets/kit/`；在源码仓库使用时，工具和模板位于仓库的`tools/`、`templates/`。确认文件实际存在，再使用其命令行帮助。不要临时发明第二套安装格式。

先区分已有二进制和需要编译源码。已有合法DLL/EXE、`plugin.json`及`payload/`时，在Windows优先运行`python tools/package_existing.py <项目目录> --out dist --installer`，生成`.zwplug`和可双击安装EXE。这条流程只需Python，不调用编译器；保留原作者的Zig/clang或其他业务构建环境，不为重新打包下载MinGW或SDK。`--sdk`仅用于可选的宿主API额外校验。省略`--installer`只生成包；HubManager仍不能直接导入裸`.zwplug`。

需要编译源码时，`templates/new_plugin.py`创建项目、`tools/build_plugin.py`构建并打包；SDK和MinGW位置由参数传入。`tools/validate_package.py`独立检查包，`tools/inspect_installer.py`核对安装EXE的嵌入内容。目标用户运行安装EXE不需要Python。

构建器先验证完整产物再发布，普通失败保留上一套完整结果；不要将旧安装器与新包混合交付。`--package-only`只交付包，会移除该版本过时的安装器及报告；完整交付使用默认模式。

`--toolchain`指向MinGW工具链根目录；该目录下应有`bin/g++.exe`、`bin/gcc.exe`和`bin/windres.exe`，不要传入`bin/`本身。构建器会自动将所选工具链的`bin`放入编译子进程PATH，并检查x64目标及预处理器依赖，不修改系统或用户PATH。

普通插件构建复用工具包的`runtime/1.1.4/`框架发行文件，不重新编译框架。`--build-framework`仅供框架维护者更新并验证发行文件；同一框架版本不得对应不同内容。

免编译安装器复用`installer-runtime/1.0.0/SetupTemplate.exe`，写入插件资源并验证代码未改变、冻结文件哈希及完整安装器内容。不要修改冻结模板或校验表；`build_installer_template.py`仅供框架维护者构建新版模板。模板本身不作为用户安装器交付。同版本内容不同须提升插件版本。

模板已提供默认图标。通过命令的`icon`声明包内PNG相对路径，`tooltip`描述用途；图标、文字、命令、资源或实现的任何发行变更都增加插件版本。身份保持稳定，同版本只允许内容完全相同的重复安装。需要真实设置与迁移示例时，参考`examples/art-notes/`，不要把演示检测参数当业务能力。

图标验收包含中望3D按钮、安装EXE以及有自建窗口时的标题栏／任务栏。源码构建的EXE自动从首个命令PNG生成应用图标资源101，窗口仍须显式设置大小图标；预编译EXE需原作者补资源后提升版本，打包不自动改写其程序。Win32窗口里的保存等业务控件不要复用`IDOK`／`IDCANCEL`，并验证通知类型和来源；Esc和关闭不能隐式触发写入，参考便签的关闭确认。

工具箱使用独立版本和兼容协议：旧安装器复用兼容的新框架，不降级覆盖。已发出的0.1.1及更早安装EXE没有这个逻辑，需重新生成；旧工具箱首次迁移必须关闭宿主。进入新机制后，框架升级可以暂存，关闭宿主后由独立更新程序提交，再启动生效。不要承诺这些旧二进制会自动获得新能力。

1. 已有二进制时保留原业务构建方式，准备匹配清单与资源；新开发时复制DLL或EXE模板，修改身份、清单和业务实现，先构建和运行该功能。
2. 已有二进制用`package_existing.py --installer`；需编译源码时才向`build_plugin.py`传入`--sdk`、`--toolchain`和`--out`。生成标准`.zwplug`和每插件一份的安装EXE，再用独立验证器检查。安装EXE首次建立框架，后续复用同一框架。
3. 在隔离目录验证包和安装事务；有宿主时，再用模型副本验证真实加载、命令和生命周期。
4. 报告实际结果、未验证部分和产物路径。没有执行过的测试，不写“已通过”。

本技能的安装验收必须包括：先装A，再装B；两者进入同一功能区；从管理器卸载A后B仍可使用；运行中操作在下次启动生效；普通卸载保留设置和日志，彻底清理只删除指定插件的数据。

还须验证单独更新A的图标与设置后B不变、同版本不同清单被拒绝、坏登记不阻断正常插件加载，以及切换安装位置后不能继续使用旧列表卸载。新框架发布另测升级、兼容复用和失败恢复，业务插件的安装成功不能替代它们。

遇到登记损坏，使用框架管理器的修复或隔离入口，按[包契约](references/package-contract.md)保留证据。不要让业务插件改写工具箱登记，也不要猜原活动版本或删除用户设置。故障注入在隔离目录进行，不要求用户破坏正在使用的安装。

技能、模板和框架一起演进。新增字段或行为先修改契约和验证器，再增加示例与测试；不要用文档承诺当前代码尚未支持的能力。
